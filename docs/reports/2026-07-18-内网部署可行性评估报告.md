# DIS 内网部署可行性评估报告

> 审查日期：2026-07-18
> 审查方式：实读代码与配置（未修改任何文件）
> 信息来源：`package.json` / `vercel.json` / `next.config.ts` / `.env.example` / `.github/workflows/ci.yml` / `docs/deployment.md` / `supabase/migrations`（共 50 个，已执行至 00048）/ `src/app/api/cron/*` / `tools/bigseller-scraper/` / `src/lib/providers/{best,golucky}/` / 全局依赖依赖扫描
> 配套文档：`docs/deployment.md` 已声明"Supabase 与 Vercel 都不是业务层永久依赖"

## 一、结论先行（TL;DR）

| 问题 | 结论 |
|---|---|
| 把 DIS 搬到公司内网运行，可行吗？ | **基本可行，但"纯物理隔离"不可行**。真正的目标形态是「内网部署 + 对少数外部端点受控出网」。 |
| 最大的阻断点是什么？ | **BigSeller 库存抓取器**：它是 Playwright + Chromium 浏览器爬虫，强依赖外网 `bigseller.pro` 且需人工维持登录态。DIS 没有它就没有数据。 |
| 技术架构是否构成障碍？ | **不构成**。应用层只用到了 Supabase 的 Postgres + Auth + RLS + PostgREST，没用 Storage / Realtime / Edge Functions；CI 已经在本地 Supabase（`127.0.0.1:54321`）跑通全部测试，证明换非云 Supabase 只需改环境变量。 |
| 内网化的主要代价？ | 自建并运维一套 Supabase（Docker 栈）、把 Vercel Cron 换成系统定时任务、保留一个受控出网通道给 BigSeller 和物流 API。 |
| 之后想再上云可行吗？ | **可行**，且成本不高——前提是内网化时保持现有供应商抽象、不把 Auth 改成不可移植的内部 SSO。 |

**一句话**：架构为你留了后路，数据来源才是硬约束。不要追求"一刀切断外网"，而要做"应用与数据落内网、仅向 BigSeller/物流开放最小出网"。

## 二、审查范围与已验证事实

### 2.1 技术栈（已确认）
- Next.js 16（App Router）+ React 19 + TypeScript strict
- 后端：**Supabase**（PostgreSQL + Auth + RLS 行级权限 + PostgREST）
- 样式/组件：Tailwind CSS 4 + shadcn/ui
- 外部抓取：Python（Playwright）写的 BigSeller 页面爬虫
- 部署：Vercel（含 `vercel.json` 两条 cron）+ 待定生产平台
- 数据库：50 个 migration（append-only，已执行至 00048）

### 2.2 关键事实（逐条实读，非推测）
1. **Supabase 用法极简**：全局扫描 `src` 未发现 `storage` / `realtime` / `channel` / `edge function` 调用。所谓 storage 命中全是 `localStorage`（列宽记忆）和文件上传 UI，与 Supabase Storage 无关。→ 应用只依赖「Postgres + Auth + RLS + PostgREST」四类能力，全部是开源可自托管的。
2. **CI 已存在且跑在本地 Supabase 上**：`.github/workflows/ci.yml` 在 `ubuntu-latest` 上跑 `test + lint + build`，并用 `postgres:17-alpine` 容器跑并发与 RLS 契约测试；默认环境变量是 `NEXT_PUBLIC_SUPABASE_URL=http://127.0.0.1:54321`。**这本身就是"非云 Supabase 可用"的最强证据**。
3. **BigSeller 抓取器是浏览器爬虫**：`tools/bigseller-scraper/bigseller_scraper.py` 用 Playwright `chromium.launch_persistent_context` 访问 `https://www.bigseller.pro/web/inventory/index.htm`，依赖首次手动登录后复用的持久化 cookie。`requirements.txt` 仅有 `playwright`。→ 必须能出网到 bigseller.pro，且宿主需装 Chromium + 维护登录态。
4. **物流 API 走外网**：百世 `BEST_OPEN_BASE_URL`、喜运达 `golucky` 均通过环境变量配置的外部基址调用，服务端发起。
5. **AI/LLM 摘要未在主代码中发现硬接线**：扫描 `glm|zhipu|openai|chat/completions|model` 无实际调用（仅 `CRON_API_KEY` 字符串匹配）。说明"AI 告警摘要"目前是设计规则/待落地能力；一旦启用，会新增一个外网 LLM 依赖（或需自托管模型）。
6. **构建期无外网依赖**：未发现 `next/font/google`、`vercel/analytics`、远程图片域名。构建可离线完成。
7. **Vercel 仅用于托管 + cron 调度**：`next.config.ts` 为空默认配置，应用逻辑无 Vercel 专有代码。
8. **cron 鉴权环境变量命名不一致**：`.env.example` 写 `CRON_API_KEY`（dry-run 路由用），而喜运达路由用 `CRON_SECRET`。迁移时需统一并补齐配置。

## 三、依赖与对外连接全景图

```
                        ┌─────────────────────────────────────┐
   内部用户浏览器 ──────▶│  内网服务器（Next.js App，next start）│
                        │   ├─ 读/写 ──▶ 自托管 Supabase        │
                        │   │      （Postgres+Auth+RLS，内网）  │
                        │   └─ cron 触发（系统定时，非Vercel）  │
                        └───────────┬───────────────┬──────────┘
                                    │               │
                      【受控出网】   │               │  【受控出网】
                                    ▼               ▼
                        bigseller.pro       百世/喜运达 API
                        （库存爬虫宿主）     （物流轨迹，可选）
                                    │
                              （若启用AI摘要）
                            LLM 端点（外网 or 内网自托管）
```

**要点**：正常运行时，应用服务器**只和 Supabase 说话**（内网）。所有外网调用都来自两类"数据注入"动作——BigSeller 爬虫、物流 API 同步（以及未来的 AI 摘要）。这意味着"内网化"的真正工作量不在应用本身，而在"数据注入通道怎么在内网下保活"。

## 四、内网可行性逐项判定

| 组件 | 内网可行性 | 说明 |
|---|---|---|
| Next.js 应用服务器 | ✅ 完全可行 | `next build && next start` 或 Docker 部署到内网 Linux/Windows 服务器，无云专有依赖 |
| Supabase（后端） | ✅ 可行（需自建） | 自托管 Supabase（docker-compose 开源栈）提供相同 PostgREST/Auth/RLS 接口，仅需改 URL/Key 环境变量 |
| 数据库结构（50 migration） | ✅ 完全可行 | 全是原生 SQL + Postgres RLS 策略，与云无关，可直接在自托管 PG 上重放 |
| RLS 权限体系 | ✅ 完全可行 | 行级安全是 Postgres 原生能力，自托管完全一致 |
| Auth 登录 | 🟡 需配置 | 自托管 GoTrue 需要设置站内 URL/回调为内网域名；邮件确认可用内部 SMTP 或关闭（内部工具） |
| Vercel Cron | 🟡 需替换 | 两条 cron 改为系统 `crontab`/`systemd timer` 周期性 `curl` 本地端点（Bearer 鉴权已就绪） |
| **BigSeller 库存爬虫** | 🔴 强依赖外网 | 必须出网到 bigseller.pro + 宿主装 Chromium + 维护人工登录态；纯隔离=无数据 |

| AI 告警摘要（若启用） | 🟡 需出网或自托管 | 外网 LLM API 或内网自托管模型（如 Ollama/本地推理） |
| CI 流水线 | 🟡 视策略 | 若"代码也不得出公司"，需迁到内部 GitLab/Gitea + 自托管 Runner；否则可继续用 GitHub |
| 构建过程 | ✅ 离线可行 | 无 google 字体/分析/远程图片依赖 |

## 五、不可行 / 高风险点 + 可行改造步骤

### 5.1 真正不可行的场景：纯物理隔离（air-gapped）
若公司要求"服务器完全不连外网"，则 **DIS 无法工作**——因为它的核心数据（海外库存）来自 BigSeller 网页，物流来自外部 API。这不是架构问题，是业务数据源的客观属性。任何"断网"方案都必须先解决数据源替代（见 5.3）。

### 5.2 高风险点（不处理会翻车）
1. **BigSeller 爬虫脆性**：浏览器爬虫本就易因页面改版/登录失效/风控而中断；在内网里它还独占一个"能出网 + 有 Chromium + 有人维护登录"的宿主，是单点故障。
2. **自托管 Supabase 运维成本**：官方栈含 Postgres / GoTrue / PostgREST / Kong / 邮件 / 存储等多个容器，需专人备份、升级、监控。小团队容易被运维拖垮。
3. **cron 出网时序**：原 Vercel Cron 在 UTC 01:00/02:00；改系统 cron 后需对齐时区并配好失败重试。
4. **Auth/回调配置遗漏**：自托管后若 `SITE_URL` / 重定向未改内网域名，登录会失败。

### 5.3 可行改造步骤（落地清单）
**A. 应用与数据库落内网（必做，约 1–2 周/1 人）**
1. 内网服务器装 Docker，部署自托管 Supabase（或仅 Postgres + GoTrue + PostgREST 最小集）。
2. 把 50 个 migration 重放到内网 PG；用 `service_role` 初始化 Admin 账号与 `CRON_SYSTEM_USER_ID`。
3. 配 `NEXT_PUBLIC_SUPABASE_URL` / anon / service_role 为内网地址；设 GoTrue `SITE_URL` 为内网域名。
4. `next build` 产物 + `next start` 部署到内网服务器（建议 Nginx 反代 + HTTPS 内网证书）。
5. 把 `vercel.json` 的两条 cron 转成服务器 `crontab`：`0 1 * * * curl -H "Authorization: Bearer $CRON_API_KEY" https://内网域名/api/cron/dry-run`；喜运达同理用 `CRON_SECRET`。统一 env 命名。
6. 防火墙只放行内网段访问 3000/Postgres 端口。

**B. 受控出网通道（必做，若保留数据同步）**
7. 在边界防火墙为**爬虫宿主**开白名单：仅允许到 `bigseller.pro`（及必要 CDN 域名）。禁止该宿主其它出网。
8. 爬虫宿主独立部署，预装 Chromium，由专人维护 BigSeller 登录态；把"登录失效"纳入监控告警。
9. 物流 API：仅在启用时开放到百世/喜运达域名的出网；不启用则可完全关闭。

**C. 数据来源加固（强烈建议，降低脆性）**
10. 评估 BigSeller 是否有**官方开放 API** 替代网页爬虫——若有，把 `tools/bigseller-scraper` 从浏览器爬虫改为 API 客户端，去掉 Chromium 依赖，稳定性与可运维性大幅提升。这是内网化里最该投入的一项。

**D. CI 策略（视公司规定）**
11. 若代码不得出公司：把仓库镜像到内部 GitLab/Gitea，配自托管 Runner（带 Docker）重跑现有 `ci.yml` 流程。Postgres 测试用容器服务，内网可跑。

## 六、内网化的优点（正向）

1. **数据不出公司**：海外仓库存、SKU 映射、供应商/物流信息全部留在内网，满足数据安全与合规诉求（这通常是做内网的根本动机）。
2. **摆脱云账单与超额风险**：`docs/deployment.md` 明确"不接受自动超额费用"。自托管后成本可控为一次性硬件/虚拟机。
3. **架构友好，迁移成本低**：供应商已被 Repository 层隔离，无专有锁定；CI 已在本地 Supabase 验证。相比一般 AI 生成项目，DIS 内网化改造量小。
4. **访问控制自主**：内网域名 + 公司网络策略即可限制访问范围，配合 Supabase Auth 做账号隔离。
5. **可离线构建/部署**：无构建期外网依赖，内网 CI/构建稳定。

## 七、内网化的弊端（反向，要如实讲）

1. **你仍然需要外网**：BigSeller 与物流 API 绕不开，内网化≠断外网。若公司期望"彻底隔离"，此期望无法满足，需提前对齐。
2. **自托管运维负担**：Supabase 栈、备份、升级、故障排查全自己扛。对小团队是持续成本，且需要至少一个懂 PG/容器的维护者。
3. **爬虫单点更脆弱**：在内网下，爬虫宿主成了"唯一能出网且有人管登录"的关键节点，人员离职/登录失效都会导致数据停更，需制度化运维。
4. **失去云厂商的可用性保障**：Vercel/Supabase Cloud 的 SLA、自动扩容、托管备份没了，可用性取决于你自己的服务器与网管。
5. **升级滞后**：自托管栈的版本更新需手动跟进，可能慢于云版本，长期有"技术债滚雪球"风险。
6. **CI/协作可能受限**：若禁止外部代码托管，需自建 Git + Runner，初期有搭建成本。

## 八、之后上云是否可行（反向迁移）

**结论：可行，且预留得好就成本低。**

- **为什么能上云**：应用层不依赖内网专有特性（无内部 SSO 硬编码、无内网域名写死在业务里）。只要内网化时**保持现有 Supabase 抽象不变**，未来上云 = 把 `NEXT_PUBLIC_SUPABASE_URL` 指回云 Supabase、应用部署到 Vercel/阿里云/腾讯云、恢复 `vercel.json` cron，即可。代码改动极小。
- **上云的优点**：免运维、自动备份与扩容、SLA、全球加速、CI 直接用 GitHub Actions。
- **上云的弊端**：恢复外网数据路径（本来就在用）、可能产生费用、数据出公司需重新评估合规。
- **反向迁移的坑（务必避免）**：内网化时**不要**把 Auth 替换成内部 LDAP/SSO 且写死到业务层、不要把"内网域名"硬编码进逻辑、不要把 cron 改成只在内网调度器里无法还原的形式。保留抽象边界，未来翻转只需改配置。

## 九、推荐部署形态与决策矩阵

| 形态 | 数据/应用位置 | 出网 | 可行性 | 适合 |
|---|---|---|---|---|
| A. 纯物理隔离 | 全内网 | 无 | ❌ 不可行（无数据） | — |
| **B. 内网部署+受控出网（推荐）** | 应用+DB 内网 | 仅白名单到 BigSeller/物流 | ✅ 可行 | 当前最现实目标 |
| C. 内网+数据源改造 | 同 B，但爬虫换官方 API | 同 B，更稳 | ✅ 可行（B 的加固版） | 长期最优 |
| D. 维持云（Vercel+Supabase Cloud） | 全云 | 天然 | ✅ 已可行 | 若合规允许 |

**建议路径**：先落地 **B**（快速见效，满足"内网运行"诉求），并行推进 **C 的爬虫 API 化**（消除最大脆点）。把"是否彻底断外网"作为立项前置问题先和网管/合规对齐——因为纯隔离在技术上行不通。

## 十一、给 Rall 的行动清单（下一步）

1. **先对齐一个前提**：找网管/合规确认"内网"是否允许「应用内网 + 对 BigSeller/物流白名单出网」。若要求纯隔离，则需先做数据源替代评估（第 3 项），否则项目不成立。
2. **立项内网化（形态 B）**：按第五节 A/B 落地，优先把 Supabase 自托管 + 应用部署跑通，用一个内网测试域名验证登录与看板。
3. **排期爬虫 API 化（形态 C）**：联系 BigSeller 看有无官方 API；有则改造 `tools/bigseller-scraper`，彻底去掉 Chromium 与登录态依赖——这是内网长期稳定的关键。
4. **迁移中保持抽象**：Auth 不写死内部 SSO、域名不硬编码、cron 留可还原结构，确保未来可上云。
5. **补运维手册**：自托管 Supabase 的备份/监控/升级流程，爬虫登录态失效的告警与重登步骤，写成 runbook。
